# R576 — opt-in rank affinity for expert readmission

R575 observed that the same SC117 expert can produce different FP16 rows across the existing PC1 and PC6 builds. The expert source previously picked a rank afresh on every admission, so eviction followed by readmission could move one expert to another producer within the same generation run. This change adds opt-in `VF_EXPERT_RANK_AFFINITY=sticky` to the SC117 prefill coordinator. It records the initial rank of each seed and every admitted (layer, expert), preserves that mapping after acknowledged eviction, and directs subsequent admissions to the same rank. If the rank lacks payload capacity, it refuses instead of silently moving the expert. Rank-local indices can change. The default is off and the previous placement behavior is retained.

The policy is applied before dynamic admissions/evictions; callers of the source API must bind it in their own execution plan. The prefill plan does so with a domain-separated `r576-` identity over the existing base/group plan. The tokenizer adapter recognizes that identity. Sticky mode currently refuses QSA tracing; batched prefill's pre-existing SSH restriction remains. The policy only keeps producer rank consistent inside this source instance: it does not prove identical arithmetic across builds, make a host immobile, authenticate producer bytes, guarantee capacity or establish cross-machine equivalence. It can cause earlier refusal where another rank has space. Existing lease/R53 gates are unchanged.

Tests: 136 library tests passed in debug and release (five pre-existing ignored); 12 prefill coordinator tests passed in both profiles; 34 tokenizer adapter tests passed using PC1's existing Python environment. A source-level test loads zero-filled synthetic sparse data, records the first rank, acknowledges an accounted eviction, then readmits the expert while an altered valid capacity profile would make the ordinary balancing policy choose the other rank. It verifies retention on the original rank; a separate case verifies rejection if that rank cannot fit the payload. This is not an actual worker eviction/reload. Independent Python SHA-256 reconstruction matches the new plan test vector. Clippy passed with the existing trace-only dead_code allowance and rustfmt passed. An initial build used stale native libraries and failed linking; an isolated rebuild of the pinned GGML native bridge corrected the test environment. No GPU, worker, R53 reservation, service change or UNKNOWN replay was performed.

Read-only PC4 inspection identified /dev/sda1 mounted as active GitLab data and /srv/zone-tempon as a separate mounted loop containing R121/R122/R124 material. No original R53 ledger was found in the bounded accessible home/zone-tempon search; this is not a complete inventory and does not establish that a backup is absent. No files or mounts were modified. The actual shared R53 and cooperative lease still need reconciliation. No full generation using sticky mode, inter-PC execution, model-level accuracy, or performance gain has been qualified.

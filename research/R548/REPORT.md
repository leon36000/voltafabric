# R548 — fail closed if a descendant keeps the engine output open

The tokenizer runner previously blocked in selector polling indefinitely if the direct engine exited but a descendant retained stdout or stderr. A deterministic synthetic fork reproduced the issue: an apparently successful direct process left its output open, and the old runner returned normally only when the descendant eventually exited. No engine, network, service or ledger was involved.

After the direct engine process exits, bounded capture now continues draining stdout and stderr for at most two seconds. If either remains open, it raises an error before parsing or releasing any receipt, with an instruction to reconcile the ledger and never replay UNKNOWN claims. The timer does not start while the engine remains alive. There is no retry, explicit signal or claim that the descendant or remote process has stopped. A slow drain exceeding two seconds can conservatively refuse a valid result; this is not a remote cleanup protocol or proof of shared lease, hardware admission or worker termination.

The regression first failed against the old runner and passes with the new one. Forty-two adapter, runner and chat tests pass with the observed local tokenizer, including inherited stdout/stderr, stderr alone, an active process exceeding the patched grace, bounded output, truncation and descriptor propagation. A separate process check with the actual two-second grace confirms that no receipt is returned while a synthetic descendant still holds a pipe. The preserved R544 complete successful v2 receipt and its prompt were revalidated through the updated adapter with a fake runner and the actual local tokenizer; the resulting tokens and decoded text match. This was a read-only receipt check, not a rerun of the model or an UNKNOWN. Python sources parse successfully.

No real GPU, remote worker, R53 reservation, service or historical ledger was touched. Raw R544 receipt and tokenizer remain on PC1; the saved-receipt check requires their restoration or recreation after formatting. The R428 expert-255 strict numerical failure and the missing shared R53/lease remain open.

# R141 — instantané de candidats du solveur pip

Le dry-run R128 téléchargeait des roues entières. Pour étudier une autre frontière, le code pip 25.0.1 de l'environnement R125 a été vérifié par SHA puis instrumenté **en mémoire** : le hook appelé après sélection des candidats par resolvelib saute volontairement la préparation finale des wheels et capture les liens retenus. Il ne modifie aucun fichier pip, n'installe aucun paquet et n'est pas un comportement standard de pip.

Le premier essai, conservé dans `initial-stderr.log`, a échoué : demander `InstallRequirement.metadata` avant la préparation complète d'une roue paresseuse provoque une assertion. Un deuxième essai distinct a corrigé le hook pour capturer uniquement nom, exigence attachée, lien et caractère demandé. Il a saisi **189 candidats** et leurs URLs. Après le hook, pip lui-même a aussi échoué code 2 quand son affichage final a demandé ces mêmes métadonnées absentes. Le fichier de candidats est donc un **instantané interne partiel**, pas un `pip report`, pas un lock, pas une installation ou une résolution complète vérifiée.

Une vérification locale avec `packaging` a extrait la version de chacun des 189 noms de wheels et confirmé sa compatibilité avec l'exigence attachée à ce candidat. Cela ne contrôle pas toutes les contraintes transitives ni les empreintes de chaque artefact. Les 188 liens réseau observés pointent vers `files.pythonhosted.org` ; le dernier est le wheel local 1Cat. Le solveur a retenu TileLang 0.1.9 et Apache TVM FFI 0.1.9, conformément aux métadonnées 1Cat ; l'override donneur 0.1.10 n'est pas qualifié ici. La borne de 128 Mio par fichier et le délai de 110 s étaient maintenus. Aucun modèle ou GPU n'a été lancé.

Suite : vérifier les 189 candidats via métadonnées de distributions et empreintes d'index, recouper toutes leurs contraintes et expliciter tout élément manquant avant d'obtenir un lock ; traiter séparément le conflit 0.1.10. Ne pas présenter les codes pip 2 comme succès.

Two fresh standalone CPU calculations used the exact R428 layer-2 expert 255 slice and token-0 activation. PC1 x86_64 and PC6 AArch64 ran the same `provider.cpp` source SHA256 f765a1ac5c9b7708b8fcc3b35469b8c89ff001e7efca78d2e31a1d08506dc042 against their respective existing GGML builds. The output FP32 hashes are 4e0c48562ba620b32901b61ee1cf3b35050e7f68f675365d2fe2a7ea3b200bb9 and 777c1f4027aeed7dff8f35962c4ba520dcacad2efc2d60d66e1fc0f54e988e98. Maximum difference is 5.401950329542e-5. Compared with the retained PC1 staged f64 reference, PC1 has zero violations and max error 2.3335928744927514e-9; PC6 has 1,167 violations and max error 5.4018620403439854e-5 at the strict prior threshold. Distinct libraries and builds mean the cause cannot be assigned to ISA alone.

A diagnostic calls the actual Rust unweighted `completion::accept_routed_output` and `moe::Collector::finish` after the same f32-to-FP16 conversion as the native worker. It uses the ten R428 route identities and original coefficients, with the nine other expert rows set to zero to isolate expert 255; the ten rows are synthetic collector receipts, not real network workers. Its expert-255 coefficient is 0.04014204069972038. Between PC1 and PC6, 1,941 of 2,560 FP16 values and Collector output elements differ; maximum contribution difference is 2.1438162605136313e-6. An independent Python `struct` binary16 oracle matches the count and maximum, and a non-finite input is rejected. Debug and release runs matched; Clippy with warnings denied, rustfmt and Python compilation passed. The standalone Rust harness uses its own recorded Cargo.lock.

This is one isolated contribution, not a whole-model error bound, a completed cross-machine run, or evidence that numerical behavior is acceptable. Do not infer full-route reduction parity or relax the R428 strict failure. A 512 MiB, zero-swap, 50% CPU scope was used on each host; no GPU, network worker or R53 reservation was launched and no UNKNOWN was replayed. Inputs and raw outputs are retained locally, not published; reproduction requires restoring the exact checkpoint inputs. The observed input hashes and host binary hashes are in PLAN.json.

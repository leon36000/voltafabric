# R528 — require a held cooperative lease descriptor for SSH generation

The SC117 SSH path previously required an expected plan and pinned host-key input but did not verify a held shared lease. The v14/r528 plan now binds a caller-supplied lease path, device, inode and UID for any SSH rank; local-only plans require no lease. Plan preparation validates the selected regular non-symlink path and UID without acquiring a lock. Before loading PLE weights or starting workers, the running coordinator requires an inherited descriptor for exactly that identity and verifies its own `/proc/self/fdinfo` contains the matching whole-file exclusive advisory FLOCK. It rechecks the descriptor and lock before each layer's workers, and before and after each generated position. A failed check returns no completed answer; operations that may already have been sent remain UNKNOWN and must be reconciled, never replayed.

The Python prompt runner passes the actual inherited descriptor to the coordinator when SSH is configured and refuses a missing/invalid descriptor before spawn. This adapts the project's recovered R53/R61 `guards/lease_contract.py` inherited-FD, dev/inode/UID and fdinfo checks; it does not acquire or unlock the real lease. The caller must independently select and hold the actual cooperative shared lease, authenticate the host and worker, reserve base plus suffix in the real R53 ledger and satisfy all resource/hardware gates. A caller-selected ordinary file or a synthetic test flock is not proof of a shared lease or that other services cooperate. Checks occur at boundaries, not continuously, and do not establish remote-process termination after a coordinator crash.

PC1 tests used a fresh synthetic zero-byte lock file only. The actual release coordinator, with a no-worker plan and intentionally invalid PLE source, refused an unlocked inherited descriptor and a different open-file description of the same locked inode. The locked inherited description passed the gate and then refused the deliberately non-regular PLE source, before workers or claims. An independent v14 JSON/SHA256 oracle reproduced the plan from `GUARD.json`. The first synthetic preflight expected a size error but received the earlier non-regular-file refusal; it made no claims and the corrected fresh test recorded the actual refusal.

Six Rust binary tests passed in debug and release; the final release build includes boundary rechecks. Tests cover no lock, exclusive lock, a second description, incorrect inode and UID, and unlock. Thirty-six Python tokenizer/adapter/chat tests passed on PC1 with the observed tokenizer; they include descriptor propagation and refusal before spawn. The CPU-only build scope used at most 3 GiB/no swap/64 tasks/150% CPU; the synthetic preflight used 512 MiB/no swap/16 tasks/one CPU. Coordinator SHA256 `7351678b5a5fa466aa600ee46714325b1a5de76829598d6bd5e34f5f2474f8ae`. No actual shared lock, SSH connection, remote worker, GPU, R53 reservation or consumed-claim replay occurred. PC6 swap remains below the 1 GiB inter-PC threshold.

Next identify and verify the actual shared lease and current R53 ledger with the owner-approved environment, bind their external admission and reconcile failure/remote cleanup before a fresh inter-PC test. This change is a necessary guard, not distributed execution qualification.

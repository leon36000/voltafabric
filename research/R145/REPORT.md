# R145 — frontière statique Skinny / TileLang

Le wheel 1Cat-vLLM 1.2.2 déjà présent sur PC1 a été relu et son SHA256 vérifié. Une lecture ZIP bornée a inspecté 1 876 fichiers Python (28 240 527 octets décompressés), sans import de code ni GPU. Les deux modules donneurs épinglés `skinny_moe.py` et `marlin.py` ne contiennent pas d'import direct de TileLang. Les deux modules 1Cat directement appelés par `moe_apply`, `moe_align_block_size.py` et `runner/shared_experts.py`, n'en déclarent pas directement non plus. Cela ne démontre pas l'absence d'import transitif, dynamique ou natif. Le chemin MoE appelle par ailleurs l'extension compilée Skinny via le chargeur Torch, ainsi que d'autres modules vLLM.

La recherche dans les sources du wheel a trouvé 12 fichiers mentionnant TileLang. En particulier, `qwen_gdn_linear_attn.py` active par défaut sa branche de préremplissage SM70 originale lorsque les deux variables de configuration correspondantes sont absentes ; cette branche importe paresseusement `chunk_gated_delta_rule_fwd_sm70_tilelang` de FlashQLA. La copie locale de ce source a été liée au SHA du membre ZIP et ses points vérifiés par AST. Ceci établit une raison concrète de ne pas déduire que le moteur complet se passe de TileLang à partir de la seule frontière MoE. Le choix effectif de cette fonction par un modèle reste non démontré.

Commandes : `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=8 pc1-lan python3 -B - < probe.py` (sortie 0), puis lecture bornée du fichier GDN et `python3 -B check.py` (sortie 0). Les octets du source GDN restent dans le sibling `.runs/r145-wheel-imports`; leur SHA est dans les reçus. Aucune installation, import runtime, génération, mesure ou modification du canonique.

Suite : identifier un petit modèle compatible et sa route GDN réelle, ou qualifier la frontière MoE isolée avec des doubles CPU ; une future installation 0.1.10 doit rester explicitement expérimentale et conflictuelle avec les métadonnées 1Cat, sans masquer `pip check`.

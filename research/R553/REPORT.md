# R553: grouped real-expert two-token CPU qualification

On PC1, two separate local guarded Rust rank sessions loaded four SHA-checked SC117 IQ3 layer-2 expert blobs (75 and 255 on rank 2; 12 and 181 on rank 3). Two observed activations from R428 were used with deliberately constructed interleaved routes and exact binary coefficients. Each session processed one unweighted FP32 batch and one ordinary FP16-result batch; both exited cleanly with two executions. The Rust session, owner, grouped execution and Collector were the production paths from R552/R551.

The independent scalar verifier compared all 20,480 unweighted FP32 elements bit-for-bit with the corresponding R551 pre-grouping provider outputs. It independently decoded each row through FP16 and accumulated coefficients in the Rust Collector's original token/slot order using f64; all 5,120 final f64 elements matched bit-for-bit. The two ledger claims remain `RESERVED_UNKNOWN_NO_REPLAY`; their returned result and clean worker receipts are additional evidence, not authorization to reuse either identity.

The run is a controlled two-token batch, not end-to-end prefill, a network test, a GPU result, or proof of speedup. Input activations are model-derived R428 fixtures, while routes are constructed for this test. The older provider baseline is not a mathematically independent expert oracle; the separate R428 strict scalar discrepancy for expert 255 remains open. The model-wide oracle and inter-PC production transport remain unqualified.

Concatenate each listed part in order, base64-decode, then gzip-decompress to recover the three inputs to `verify_batch.py`.

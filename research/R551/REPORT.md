# R551 — reuse quantized activation within a rank batch

The existing native GGML CPU rank worker quantized the same token input again for every selected expert. `RankWorker::execute_f32` now prepares it once per `(token, gate_up_type)` in a batch-local map and passes an opaque prepared input to each matching resident. The map is destroyed at the end of the batch. Different tokens or gate/up formats cannot share an entry. Slot order, unweighted FP32 outputs, routing coefficients, resident bindings, existing Collector contract and terminal-on-error behavior remain unchanged. The separate `Fleet` path retains its existing implementation. The prepared path checks the format again at both Rust and C++ boundaries and stages outputs before returning them.

This is an original adaptation of the existing local GGML CPU type-trait boundary, whose source records Strata `fb58e0dbc8399662c0e47c76578c6e878b14f6cf` and llama.cpp `3cf03257f219afbe7334045ff7c6a06ac68c627d` (MIT). The PC1 native library uses the existing isolated GGML archives described in R400; their complete build provenance is not asserted. No QPN2, NVFP4, MXFP4 or IQ3 formats are equated. No timing or throughput comparison was made; fewer preparation calls do not by themselves prove a performance gain.

A C++ regression was first compiled against the old interface and failed because prepared inputs did not exist. The final provider/bridge test passes all seven supported type pairs, rejects invalid inputs and a prepared input for another format without publishing output, and retains the previous scalar checks. The new Rust batch regression interleaves two inputs and two resident experts and verifies exact output and slot order. Eight native-provider integration tests pass on PC1 in debug and release, including actual local synthetic child sessions; release Clippy and rustfmt pass. The first isolated integration build lacked explicit binary targets; after those targets were added, the tests passed.

Separately built old and new native libraries were run on 12 locally observed layer-2 expert slices and two R428 activations: all 61,440 FP32 values were byte-identical, including expert 255. Four combinations were cross-input probes rather than actual routes; these activations came from synthetic perturbations of a model-derived residual. This establishes preservation relative to the old provider for these samples, not full numeric correctness. R428 expert 255's 1,169 strict scalar violations remain unresolved.

A fresh one-shot PC1 CPU generation then used the new worker and sealed coordinator under new run/attempt identity and a fresh local ledger. It processed 73 prompt tokens and emitted the same 20-token response ending in EOS as R550. All input, embedding, final-layer output and logits hashes match R534 across 92 positions; the layer-3 trace is byte-identical to R544. All 96 workers closed; stderr was empty. The verifier checked 20,709 claims, including 16,293 evictions, and all 6,198 distinct experts against prior local source observations. There were 6,589 compact raw worker executions. Claims remain UNKNOWN and must not be replayed. A live local worker's executable hash matched the new bound worker, but this is not remote attestation.

Independent NumPy checks of the actual trace again passed the layer-3 hyperconnection and attention boundaries; they consume observed upstream values and do not establish full-model parity.

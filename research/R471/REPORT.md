# R471 — independent activation-quantization boundary check

Parent R470 `d56ca8da7d9a2b85b6c327004a120562b2e39c2f`. The R428 expert-255 discrepancy remains open: a scalar/vector intermediate difference changed one quantized byte. This work investigates a separate but relevant source of ambiguity without executing the R428 worker, replaying its claim or running GPU code.

`quant_probe.cpp` uses the existing GGML CPU traits selected for IQ4_NL and IQ2_S to obtain their activation quantizers, respectively Q8_0 and Q8_K, and emits both the optimized CPU output and GGML's scalar `_ref` output. `verify_quant.py` independently implements the Q8_0 and Q8_K block packing in Python, including float32 rounding, Q8_0 half-scale and ties-away rounding, Q8_K signed maximum, nearest-even integer rounding and block sums. It imports no GGML or NumPy. The GGML paths are still reused components, so this isolates activation packing; it does not independently validate the model's IQ weight decoders or dot products.

On a saved R428 layer-2 input activation (SHA256 `c8a0744a87fade2652acfb34c802a49354379f558791bdf63e53f1f124bcc88a`), Q8_0 and Q8_K independent, scalar-reference and optimized packed outputs were byte-identical on both PC1 x86-64 and PC6 aarch64. This input is not the expert's post-SiLU intermediate used for R428's down projection, and this observation is not a pass for that expert's full scalar oracle.

A separate synthetic vector contains exactly representable half steps with a Q8_0 scale of 1. On both CPUs the independent ties-away result matched GGML's scalar reference exactly, while the optimized Q8_0 path differed in 480 code bytes across 80 blocks and matched an independent nearest-even implementation exactly. For example, `0.5` and `-0.5` become `1` and `-1` in the scalar reference but `0` and `0` in the optimized path; `2.5` becomes `3` versus `2`. Q8_K matched its scalar and independent nearest-even result on this vector. This proves a specific rounding-contract difference for the tested CPU builds and inputs, not that this exact tie caused R428's expert-255 failure or that all inputs/architectures behave identically. The full R428 failure and its original tolerance remain unchanged.

The inspected `ggml-quants.c` SHA256 is `07143d7068936ae46b3c528b2f3d4bbb666e74d88992165716174d243573965d` on both; `ggml-cpu.c` and `quants.c` hashes also match. GGML/llama.cpp is MIT licensed; this diagnostic calls the existing builds and records their actual static-library hashes below. Binary builds differ by architecture. `verify_cases.py` checks the four result summaries and the expected boundary behavior. Probe builds used `-Wall -Wextra -Werror`; the small CPU probes ran in 512 MiB, zero-swap, one-CPU scopes. The saved 10 KiB activation was copied read-only to a fresh Naos scratch directory for the PC6 calculation. No worker session, GPU, R53 lease or distributed expert execution was used.

Next define and test an explicit activation-quantization rounding contract across supported CPU/GPU providers, then construct a complete independently decoded expert oracle around quantization boundaries. Do not change the model's quantization format or claim full-model parity from these samples.

# R467 — bounded route-protected local CPU eviction policy

Parent R466 `3e94cbe342fbea16ca8522bd4548c30ca17511ff`. `Segment::evict_to_target` adds caller-invoked selection between committed positions. Each successfully committed layer records its gate's expert IDs. The planner excludes those IDs, sorts candidates deterministically by layer/expert/rank, keeps at least one resident per rank and limits a call to at most 64 removals. It computes the entire feasible plan with checked payload accounting before sending anything, reconstructs and validates every selected binding, and uses R464's durable reservation and exact worker acknowledgement for each removal. An infeasible plan returns without eviction or reservation. If a later acknowledgement fails, earlier confirmed removals remain applied and the segment is poisoned; this is not an atomic multi-eviction transaction.

The last committed route is a protection heuristic, not knowledge of the next gate. The target is accounted expert payload at the time the method returns, not an RSS limit or a guarantee that the next position fits. Selection is deterministic and caller-invoked: it is not an automatic pressure trigger, an LRU implementation, a topology-aware distributed placement policy or a claim of performance improvement. Successful acknowledgement and no-replay handling remain local CPU semantics; the ledger is not R53 or a hardware lease.

A fresh PC1 CPU run used the real 48-layer SC117 path for input IDs `[9419, 0, 1165]`. After position 0, an intentionally infeasible target with a one-eviction limit was refused, with no change to accounting, cursor or claim count. A two-eviction call then removed layer-0 experts 0 and 1 from ranks 2 and 3; neither was among the previously observed gate's ten chosen experts. It released 4,352,000 accounted payload bytes in total, and both later positions completed. All three embedding and layer-output hashes and both logits hashes equal R464; output IDs were `[1165, 3849]`, and all 96 workers closed normally. `verify.py` checks the two actual eviction receipts against their persisted claims and R466's separately observed gate, batch coverage, exact output hashes and final accounting. No RSS or throughput improvement is measured.

The fresh run retains 144 batch and two eviction claims, all `RESERVED_UNKNOWN_NO_REPLAY`; no UNKNOWN was replayed. Its CPU-only systemd scope used MemoryHigh 11 GiB, MemoryMax 13 GiB, zero swap, TasksMax 320 and CPUQuota 300%. No GPU, inter-machine transport, R53 lease or shared hardware operation was used; no rank-session remained afterward. The execution sources and Cargo manifest matched between PC1 and PC6. Seven focused Segment tests passed in both debug and release on PC6; targeted Clippy passed on the PC6 library and PC1 release diagnostic, and rustfmt and `verify.py` passed. An attempted release library-test build on the compact PC1 project failed because eleven unrelated included fixtures/evidence files were absent; the successful PC6 test used the full local project.

This does not establish independent full-model numerical parity, checkpoint authenticity, arbitrary workloads, future-route residency, inter-machine execution or GPU compatibility. Further work must test a later-eviction acknowledgement failure in a multi-removal plan, integrate a budget/pressure trigger without dropping an in-flight route, investigate workload-specific placement and build an independent model oracle.

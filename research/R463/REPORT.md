# R463 — acknowledged local CPU native-expert eviction

Parent R462 `42f1b86d0bfa7f609bf81b29a87a567c12b4dfb5`. Adds an opt-in, capability-negotiated native GGML eviction request to a sealed local CPU rank session. The worker accepts it only after a successful local execution, with the exact last full run/model/plan/layer/batch/epoch stamp and attempt, a unique SHA256-shaped operation ID and exact expert binding. It refuses an unknown or changed binding, a reused operation ID, a stale stamp or removal of the last owner. It removes the resident, returns its payload size and remaining count, and preserves the order of remaining owners and execution history. The client verifies every acknowledgement field and marks the session unusable on lost, refused or mismatched acknowledgement. The worker's operation-ID set is in memory only: the caller must durably identify and reconcile operations, ensure the enclosing distributed batch committed globally, update registry/order and accounting only after verified acknowledgement, and never replay UNKNOWNs.

A fresh PC1 CPU run used one actual native worker with real layer-0 experts 434, 308 and 37 and a synthetic activation. After a committed Collector result for expert 37, it evicted expert 308, reporting 2,176,000 resident payload bytes removed; the retained expert 37 gave the identical FP16/f64 Collector output after the physical ordering changed. It then appended real expert 309 and obtained a different valid output; the worker executed three batches and closed with BYE. All four expert digests match the independent local pack/GGUF slice observations already preserved in R462. The diagnostic keeps input blobs in the controller during the test, so reported payload removal is not a measured total RSS reduction. Three batch claims remain `RESERVED_UNKNOWN_NO_REPLAY` in `CLAIMS.json`; the recorded eviction operation ID must not be replayed.

Three focused synthetic tests passed in debug and release: real child/session/Collector execution with two distinguishable weights and correct physical remapping; pre-completion, stale stamp, wrong binding and last-owner refusals; and lost or incorrect acknowledgement leaving the client unusable. Duplicate operation rejection is exercised. Three existing append-owner tests and 28 default session tests passed; strict native-feature Clippy and targeted formatting passed. The PC1 source and Cargo.lock hashes match the local execution sources. A dedicated CPU-only scope bounded the real test to 2 GiB, no swap, one CPU and 16 tasks. No GPU, inter-PC worker or R53 lease was used; no worker remained after completion.

This is an explicit worker/session boundary, not an integrated cache or automatic eviction policy. Source accounting and `Segment` are intentionally unchanged: they still do not reclaim the payload budget or choose victims. Next add durable per-operation reservations and transactional registry/source accounting, protect currently routed experts and test failure/UNKNOWN reconciliation before enabling eviction in longer generation. Full-model numerical parity, checkpoint authentication and actual cross-machine/GPU execution remain outstanding.

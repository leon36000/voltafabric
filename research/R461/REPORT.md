# R461 — bounded text prompt through the 48-layer local CPU chain

Parent R460 `95b23f6fcabf1a0afe1185f1f1d027d33cafd5a5`. `vf-sc117-prompt-greedy` accepts a caller-selected ordinary input token, loads all 48 observed SC117 layers and the existing head, and executes at most two greedy positions with actual route-driven local expert owners. It no longer performs the shared-component pre-execution preview from R459. EOS ends the token loop; no token is fed after EOS. The code remains explicitly an experimental CPU qualification, with no chat template, general multi-token prompt prefill, sampling, extended context, authenticated model provenance, GPU or distributed transport.

`adapters/strata_tokenizer/prompt_runner.py` reads text from stdin, validates a pinned tokenizer and executable, permits exactly one ordinary prompt token, invokes the engine once using explicit absolute paths, checks the complete returned receipt and decodes it only after successful worker shutdown. It does not retry failures; a caller must use an independently admitted resource scope, a fresh ledger, reconcile any uncertain run and never replay UNKNOWN claims. The returned JSON includes full technical receipt; neither it nor hashes authenticate the model or receipt publisher. The four tokenizer pack files and regex dependency are external and caller-provided. The temporary stdout/stderr capture is checked against a limit after subprocess completion, not an OS-enforced pipe-memory limit.

A fresh PC1 CPU run tokenized `Hello` to ID 9419, then the actual 48-layer chain emitted IDs 11 and 353, decoding to `, I`: the combined example is `Hello, I`. The stop reason was the two-token limit, not EOS. All 96 local workers executed both positions and closed normally; 96 seeds and 690 dynamically loaded experts consumed 1,611,699,200 bytes under a 3 GiB expert-payload cap. A separate Python observer verified all 786 loaded pack payloads against the corresponding local GGUF slices and source hashes (`WEIGHTS.json`). This is local consistency, not publisher authentication or an independent numerical oracle.

A second fresh run took `K` (ID 42) and produced IDs 3649 and 1277 (`ıbr`). Its two final residual hashes, full-logit hashes, seed hashes and admission bindings exactly match R459, despite R461 omitting the preview. That is a regression comparison sharing numerical components, not independent full-model parity. Both runs used independent identified ledgers and resource scopes: MemoryHigh 10 GiB, MemoryMax 12 GiB, zero swap, TasksMax 320, CPUQuota 300%; systemd reported 10 GiB peak for each. No rank worker remained afterwards. Each ledger's 96 claims remain `RESERVED_UNKNOWN_NO_REPLAY` in `CLAIMS.json`. No GPU, inter-PC execution or R53 lease was used.

Eight Python tests passed on PC1, including single-token restriction before spawning, no retry on failure, rejection of mismatched receipts, UTF-8/EOS policy and pinned pack mismatch. Strict Rust Clippy and targeted rustfmt passed; release CLI refused EOS, out-of-range and malformed prompt IDs before file access. EOS behavior itself is covered with a synthetic decoder test, not a live model-emitted EOS. PC1 and local source hashes match. The test has two supplied prompt examples and only two generated tokens each; it is not a benchmark or a useful conversational result.

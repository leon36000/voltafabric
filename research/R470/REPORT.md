# R470 — four-token local CPU generation and five-position QSA

Parent R469 `5550a83daa276c61b9cc9ae9e870271cfb788005`. The existing `vf-sc117-prefill-greedy` qualification binary now accepts an optional maximum of one to four new tokens (default two, retaining the old command). It allocates QSA capacity for exactly `prompt length + maximum new tokens - 1`, advances each prompt/generated input once and stops on EOS. The tokenizer prompt runner forwards a nondefault bound and verifies it against the receipt. Receipt decoding now accepts up to four generated tokens and five input positions, refuses a non-EOS result shorter than the requested bound, and continues to validate token order, EOS, hashes and complete worker shutdown before releasing text. These are explicit experimental bounds, not general-length generation.

A fresh PC1 CPU run tokenized `Hello!` as `[9419, 0]`, advanced `[9419, 0, 1165, 3849, 13293]` through 48 layers and generated `[1165, 3849, 13293, 421]`, decoded as ` We’ve noticed that`. The stop reason was the four-token limit, not EOS. All 96 local worker sessions closed normally. The first three input, embedding and layer-output hashes and the first two logits hashes match R462. The subsequent positions and output are not compared against an independent full-model oracle.

The run admitted 1,253 dynamic experts in addition to 96 seeds, with 2,777,446,400 accounted payload bytes under the 4 GiB limit. `verify_new_weights.py` reused R462's independent local observations for 1,003 experts and independently compared the 346 additional admitted expert digests against local pack blobs and GGUF slices. `verify.py` checks all 1,349 observed experts, the autoregressive receipt and reference prefix, and the complete 48-by-5 claim set. These observations prove local consistency, not publisher authentication or general model accuracy.

The fresh local ledger contains 240 batch claims, all `RESERVED_UNKNOWN_NO_REPLAY`; no UNKNOWN was replayed. The CPU-only execution scope used MemoryHigh 11 GiB, MemoryMax 13 GiB, zero swap, TasksMax 320 and CPUQuota 300%. The separate observer used 2 GiB maximum, zero swap, 16 tasks and CPUQuota 100%. No GPU, inter-machine worker, R53 lease or shared hardware operation was used; no rank-session process remained after execution. PC1 and PC6 hashes match for the binary source, adapter, prompt runner, runner tests and observation script.

Ten Python tokenizer/runner tests passed on PC1, including four-token sequence, incomplete receipt refusal, backwards compatibility, bounded input and observed tokenizer digest. Local PC6 system Python lacks `regex`, so the same Python tests could not run there; PC1's existing Strata environment supplied it. Five QSA tests passed debug and release on PC6, including an independent five-cell analytical causal-softmax calculation and overflow refusal. The Rust CLI refused output limits 0 and 5 before opening input paths; targeted release Clippy and rustfmt passed. The verifier checked the completed receipts and claims.

This CPU result does not prove unrestricted generation, an authenticated checkpoint, full-model numerical parity, actual multi-machine transport, GPU compatibility or measured performance. Next extend prompt/output handling under a measured memory budget, verify later state/logits against an independent model oracle, and continue the distributed hardware admission work.

# R565 — dynamic GDN segment batch on actual CPU owners

Adds `Segment::advance_gdn_batch_with_source` for one non-PLE GDN layer. It checks position, attempt and finite inputs before reserving, then binds the actual GDN/post-attention route, bounded expert source, shared expert and native Collector. Missing experts are admitted before dispatch; there is no eviction in this operation. Once a reservation begins, any error poisons the segment and no residual is returned. On success, resident usage, active ranks and cursor advance together. PLE and multiple layer-major stages are not yet integrated into this method.

One bounded PC1 CPU run, with fresh separate fault/success ledgers, used SC117 layer-4 weights, the R432 residual and a second residual scaled by 1.001. Two initial residents were seeded; 11 additional routed experts were admitted after their pack slices matched the source GGUF. Two guarded local rank sessions each processed one grouped request and exited cleanly. Both residual hashes match R563's serial native Collector results; the first matches R432's independently reconstructed result. With a payload budget of three expert blobs, the source admitted one expert then refused; the segment became terminal, returned no output and refused a further attempt. The two receipts remain RESERVED_UNKNOWN_NO_REPLAY and are included.

The diagnostic binary was built before copying R561's added standalone GdnBatch API into this isolated worktree; the pre-existing GdnState step and the used GDN stage/transaction code are unchanged by that addition. Its source files for the QSA chain were current. Later testing copied all current non-bin Rust source files into the worktree and verified their hashes against PC6. Native-feature Clippy passed with the existing trace-only dead_code allowance; fresh debug and release library tests each passed 133, with five ignored; formatting passed. The previous R564 test worktree included earlier QSA/chain files, so its suite result alone did not cover the current QSA/chain. R565's new runs correct that coverage limitation. None is a full repository test or model qualification.

A CPU scope limited the actual run to 3 GiB, zero swap and 100% CPU quota; no GPU or inter-PC worker ran. The second position is synthetic and lacks a new independent numerical oracle.

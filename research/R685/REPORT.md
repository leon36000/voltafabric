# R685 — R659 Q8_0 GGUF through donor top-1 MoE and registry mapping

## Change

The pinned llama.cpp/GGML CPU graph now consumes the exact Q8_0 tensor payload layout generated by the existing R659 Rust fixture (`tests/gguf_moe_layout.rs`): one Qwen2MoE layer, hidden/FFN width 32, two experts, separate gate/up/down tensors, GGUF v3. The small C++ fixture writer reproduces the checked-in R659 metadata ordering, dimensions, type IDs, scale/code payload recipe, and 32-byte data alignment; the pinned donor parser reloads all three tensors and validates their physical spans and payload bytes before graph construction.

The donor's own sigmoid and top-1 selection are used (`selected_experts_in == nullptr`); gate, up, SiLU, and down run through the pinned `build_moe_ffn`. The R659 resident order `[40, 3]` maps to checkpoint indices `[1, 0]`. This exposed a missing bridge conversion: donor route IDs are checkpoint indices, while the VoltaFabric collector needs registry expert IDs. `RouteBatch::checkpoint_expert_to_registry_expert` provides this explicit projection. Dynamic routes now validate that mapped IDs are in range and injective, translate the selected checkpoint ID once, then resolve the owner from the VoltaFabric registry projection. Empty mapping retains the prior identity behavior.

## Verification

- Pinned donor: llama.cpp/GGML commit `3cf03257f219afbe7334045ff7c6a06ac68c627d`, MIT; donor GGML source remained unchanged.
- Direct R685 runner compiled with C++17, `-Wall -Wextra -Werror`; four live `process_ubatch` CPU graph cases passed.

- A scalar Q8_0/SiLU oracle matched donor raw outputs within a stated `1e-3` relative tolerance. The collector result matched `raw * final_weight` within `1e-6`, proving one application at this bridge boundary.
- A third case returned `provider_failure`; `process_ubatch` returned null/FAILED, detached the hooks, and the capture had no published output.
- A fourth case supplied a duplicate checkpoint-to-registry projection; graph construction failed before the collector callback, with no result or published output.
- R684's prior F32 GGUF `build_moe_ffn` runner passed again with the new optional ID map empty, preserving identity behavior.

## Reuse and limits

Reused the pinned donor's real GGUF parser, Qwen2MoE top-1 gate, Q8_0 matmuls, SiLU path, down projection, and live `process_ubatch` hook. Reused the exact tensor-byte recipe from the R659 runtime fixture, but generated a fresh local file because R659 does not persist its generated GGUF artifact. No donor generation loop, scheduler, model loader, or production checkpoint is used.

This is a CPU bridge and synthetic one-layer fixture. It does not run the R659 Rust expert-slice loader and donor graph in one end-to-end process, use a production checkpoint, qualify fused gate/up or expert top-k greater than one, test full-token generation, GPU/V100, inter-PC/RDMA, production R53, or performance. The `1e-3` relative raw-output tolerance accommodates the donor CPU SiLU implementation; the route multiplication check remains much tighter. The isolated R685 adapter copy omits unrelated source files referenced by the full `CMakeLists.txt`, so full CMake configure/CTest registration was not qualified here; the direct runner is the test evidence.

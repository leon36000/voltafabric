# R128 — limite de la résolution pip en mode dry-run

Une seule exécution `pip install --dry-run --ignore-installed --only-binary=:all: --no-cache-dir --retries 0 --index-url https://pypi.org/simple --report … <wheel 1Cat R125>` a été lancée sur PC1, dans une zone temporaire privée Naos, avec limite fichier de 128 MiB et délai de 110 s. Le wheel 1Cat a été re-haché avant lancement. Aucun paquet n'a été installé et aucun GPU, modèle ou import 1Cat n'a été exécuté.

Le processus pip s'est terminé avec **code 1** : `OSError: [Errno 27] File too large`; aucun rapport de résolution final n'existe. Le journal montre que, malgré `--dry-run`, pip a téléchargé des roues pour préparer son résultat ; `flashinfer_cubin` annonçait 360,9 MB et son téléchargement s'est arrêté à environ 134,2 MB à la limite déclarée. Le code SSH 0 de l'enveloppe indique qu'elle a enregistré le résultat de pip, pas que pip a réussi. Les sorties intégrales et l'intention bornée sont conservées ici.

Cette expérience élimine l'hypothèse qu'un `pip --dry-run` suffit à obtenir gratuitement et sans gros fichiers une résolution complète. Elle ne démontre ni un défaut de pip, ni une incompatibilité GPU, ni la liste complète des dépendances. Il faut désormais construire une résolution bornée à partir des métadonnées d'index et des fichiers PEP 658 hachés lorsque disponibles, expliciter les dépendances manquantes et les tailles, puis admettre les véritables artefacts avant toute installation ; ne pas relancer ce même essai en relevant silencieusement la limite. Les contraintes contradictoires TileLang/TVM FFI restent explicites.

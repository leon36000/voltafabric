# R549 — execute the verified engine bytes

The prompt CLI hashed the engine path and later launched that path, allowing a different executable to be substituted in between. A test using temporary copies of `/usr/bin/true` and `/usr/bin/false` reproduced the substitution: the original runner executed the replacement. This involved synthetic files only.

On Linux, the CLI now opens the caller-selected regular executable without following its final symlink, checks execute access and the 128 MiB bound, copies its ELF bytes into a private memfd while hashing and checking source identity, seals the snapshot against writes, growth and shrinkage, checks the sealed snapshot digest, and executes the inherited descriptor. It never falls back to the original pathname. Script executables and environments without the required Linux memfd/sealing/proc support are refused. The memory scope must account for the additional snapshot up to the executable cap. The source path can subsequently be replaced or modified in place without changing the snapshot; this is local byte identity, not publisher authentication or a defense against a privileged hostile process.

`run_prompt` accepts the already sealed descriptor from the CLI and passes it alongside, but distinct from, the existing shared-lease descriptor. Direct library users remain responsible for authenticating the descriptor and their execution path. The plan identity, model formats, routing, reduction and no-UNKNOWN-replay rules are unchanged.

The initial replacement test failed before the change and passes afterwards. The suite of 46 tokenizer, runner and chat tests passes with the observed local tokenizer, including path replacement, in-place mutation, rejected writes to the sealed descriptor, invalid digest, script, symlink, no execute permission, unsealed descriptor, and forwarding the binary and synthetic lease descriptors together. Tests used fresh synthetic files and did not acquire a real lease.

The actual local coordinator SHA256 `76b062606fff9bee11649acde0331e6b1a7d2dd1fb6a58b27481e7e679042788` ran through the sealed-descriptor CLI in plan-only mode and produced the byte-identical R544 plan, file SHA256 `5c89571f7a20c0101070e43ef09dd1574970a5e33e2ad386b482fd965ec0d234`, independently reconstructed by `research/R544/verify_plan.py`. No worker, native claim, GPU, inter-PC transport or hardware reservation was started. A first plan-only attempt stopped before launch because the earlier R544 coordinator hash no longer matched after a prior rebuild; the subsequent attempt pinned the newly observed binary and left the fresh ledger empty. This is not a full-generation qualification of the new binary.

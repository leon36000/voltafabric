# R468 — caller-selected headroom before a local CPU token

Parent R467 `b10bc4c7a706fe01c1fa36e65c2c5a94e4e0a19a`. `Segment::advance_token_with_headroom` connects a caller-supplied expert-payload margin to R467's route-protected policy before starting a position. It first validates segment state, attempt, input and the PLE token; it checks the source's accounted limit and uses checked arithmetic. If the current payload leaves less than the requested margin, it trims to `limit - margin` with the caller's bounded eviction count, then starts the ordinary source-backed advance. If no trimming is needed, it does not evict. If pressure exists before any position has committed or the plan is infeasible, it refuses before dispatch. A later batch failure returns no partial token output; already acknowledged prior evictions remain applied.

The margin is requested by the caller, not a prediction or reservation of the next gate's experts, an RSS bound, a measured pressure signal or automatic placement across machines. The previous route is protected, not future routes. The normal source budget remains the hard bound during loading; a future position can still fail safely if its actual demand exceeds available capacity. The existing explicit advance remains available; this method is opt-in.

A fresh PC1 CPU diagnostic ran the real 48-layer SC117 path with prompt IDs `[9419, 0]` and next input 1165. Position 0 advanced with no requested margin. Before position 1 the diagnostic deliberately requested a large margin computed from the observed current payload so that two evictions were necessary; stale attempt, invalid PLE token and an infeasible one-eviction limit were each refused with no cursor, source-budget or claim-count change. The valid call then evicted layer-0 experts 0 and 1, each 2,176,000 bytes, before executing the position. Both were outside the separately observed last route. Position 2 advanced with zero requested margin. All three embedding and output hashes and both logits hashes match R464, output IDs are `[1165, 3849]`, and all 96 workers closed normally. `verify.py` checks the two receipts against 146 persisted claims, the R466 route and R464 result; the invalid-input checks are assertions executed by the diagnostic before the valid call.

Its CPU-only scope used MemoryHigh 11 GiB, MemoryMax 13 GiB, zero swap, TasksMax 320 and CPUQuota 300%. No GPU, inter-machine transport, R53 lease or shared hardware operation was used. This demonstrates a deliberately induced headroom trigger in a local CPU qualification, not realistic headroom sizing, RSS reclamation, throughput improvement, authenticated checkpoint provenance, independent full-model parity, distributed transport or GPU compatibility.

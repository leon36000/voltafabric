# R540 — strict verdict plus a separate quantization explanation

This experimental local CPU diagnostic extends R539's expert reference. It keeps the original full scalar comparison and its tolerance `1e-7 + 1e-3*abs(scalar)` as a separate verdict. For each of the 640 gate, up and intermediate values it also checks scalar/vector agreement using that tolerance. It then computes, for each down-projection row, `sum_j abs(weight_j)*abs(dequantized_vector_j - dequantized_scalar_j)` and checks that the absolute difference between provider output and scalar reference does not exceed this quantization envelope plus the staged-down tolerance `1e-7 + 1e-3*abs(staged)`. The independently accumulated staged down projection must also meet that staged tolerance. The envelope explains an error; it does not replace the original strict result.

On the observed R428 token-0 input and layer-2 expert 255, gate/up/intermediate checks and the envelope had zero violations, while the unchanged strict scalar check had 1,169 violations. The program therefore returned exit 19 and `STRICT_FAIL_BOUND_EXPLAINED`; it did not emit a successful reference artifact. Expert 75, with the same observed activation, produced zero strict and envelope violations and `STRICT_PASS` with exit 0. Both are local numerical observations; they do not establish a general acceptance standard or resolve the strict failure for expert 255.

Negative controls on expert 255 changed a vector intermediate by 0.1 and a provider output by 0.1 in memory. They were rejected with exit 17 (intermediate threshold) and exit 18 (envelope), respectively, before any reference artifact was emitted. The valid probe used the retained R428 activation and local pack data; its GGML quantizers and dequantizers are shared with the provider. The scalar sums are separately accumulated. No worker, ledger claim, GPU, inter-PC transport, or original UNKNOWN was replayed. Local CPU scopes used MemoryMax=512 MiB, SwapMax=0 and CPUQuota=50%; compilation used the previously isolated GGML libraries and headers.

`python3 research/R540/verify.py` checks the retained record and classifications, not a fresh mathematical recomputation. The raw checkpoint and activation are not published; rerunning the native diagnostic after PC1 format requires restoring or recreating them. `STATUS.json` records the observed process exits. The diagnostic has not been integrated into the runtime and does not justify accepting an explained strict failure as a production pass.
